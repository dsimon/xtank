## 1. Objective

Present shared server-authored roster/config/ready/start/results/lobby state and
admin transfer on both clients; make authority server-authored (never guessed
from the WELCOME player role); enable config/start/reset only for the
administrator with an independent server-side rejection; keep both mazes and
all approved drone configurations selectable; invalidate readiness on a config
revision change; make results→lobby, error/disconnect→connect and fresh join
work without a process restart and without a solo auto-start racing the second
player; and ensure wrong peer/channel/session/stale-epoch datagrams cannot
regress client state.

## 3. Implementation

### 3.1 Authority is server-authored, never guessed

The P2 client set `is_admin` from `WELCOME.role == 1`; the P3.1 server always
sends `role = 1` ("player; never administrator"), so every peer looked like an
administrator. P3.10 removes that guess entirely. Administrator authority now
comes only from `LOBBY_STATE.admin_index`, compared with this client's
`LOBBY_STATE.self_index` (`session_client.c` and `menu.c`). The fixture proves a
player whose WELCOME role is `player` (1) is **not** admin until/unless the
server authors it, and that the non-admin is refused both by the local UI gate
and independently by the server.

### 3.2 Roster / config / drone / readiness presentation

`session_client.c` reduces `LOBBY_STATE` into a bounded roster copy plus the
shared config revision, drone count, maze/vehicle id and wire session state.
`menu_build_lobby` renders each roster entry (`*` admin, self highlighted,
`ready`/`waiting`/`left`) and the `Drones:`/`Config rev:` fields. The fixture
builds the lobby scene on both clients and asserts both names, the mazes/
vehicles/drones/revision labels and the roster readiness.

### 3.3 Admin-gated controls with independent server rejection

`frame_lobby_select_config`, `frame_request_start` and `frame_request_reset`
return `-1` without sending unless `menu_lobby_can_*` holds (connected,
server-authored admin, correct session state). The fixture additionally bypasses
the local gate and sends `CONFIG_SELECT`/`START_REQUEST`/`RESET` from the
non-admin over the real transport; the server rejects each with
`PROTOCOL_ERROR`/`XTK_ERR_NOT_ADMIN` and the shared revision/state is unchanged.

### 3.4 Revision readiness rule (D3-B)

Readiness is always sent with the current tracked `config_revision`
(`session_client_send_ready`), and the client clears local readiness whenever a
`LOBBY_STATE`/`CONFIG_STATUS` reports a new revision. The fixture selects
combat1+2 drones (rev 1), Arena+1 drone (rev 2) and combat1+0 drones (rev 3),
asserting the revision is shared by both clients, the config is visible to the
non-admin, and readiness is cleared after each change before both ready against
the final revision.

### 3.5 Results→lobby, admin transfer and in-process rejoin

`LOBBY_STATE` drives the session state, so the reset barrier moves both clients
from Results back to Lobby and clears the retained results. On departure the
server transfers the administrator and broadcasts `LOBBY_STATE`; the fixture
asserts the survivor inherits `admin_index == self_index`. `frame_reconnect` +
`session_client_connect` rejoin a fresh session in the same process (the client
transport keeps a spare peer slot so the new connection opens while the released
one drains); the fixture asserts the rejoining client is not admin and the
survivor remains admin.

### 3.6 No solo auto-start racing the second player

On a server whose `WELCOME.human_capacity > 1`, `frame_lobby_step` never
auto-configures or auto-readies, because a lone peer that configures would let
the server's solo auto-start claim the session before the second player can
join. The shared lobby waits for the administrator's explicit config/ready/start.
The fixture connects A alone on a two-human server, runs idle ticks and asserts
the server stays in Lobby with no config revision, then connects B into the
same lobby.

### 3.7 Inbound validation and lobby liveness

`session_client_ingest` rejects a datagram from a foreign peer, a transport
channel that disagrees with the message class, a foreign session id, and a live
epoch older than the highest seen (START/EPOCH_BEGIN carry the new epoch), all
before any state change. The fixture injects a foreign-peer `LOBBY_STATE`,
a wrong-channel message, a foreign-session `LOBBY_STATE` and a stale-epoch
`RESULTS` and asserts the client state does not regress, while a current-epoch
`RESULTS` is accepted. A 0.5 s lobby PING (`XTK_MSG_PING`) keeps an idle lobby
peer's valid-input clock fresh (D3-E) so the UI can stay open for rejoin.

  rejoins a fresh lobby; a lobby heartbeat keeps the idle peer alive.

  stale-epoch datagrams are rejected before any state change.
