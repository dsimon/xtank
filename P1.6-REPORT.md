## Config / player-binding design

`Src/Include/server.h` defines `ServerConfig`/`ServerPlayers`: an ordered list of
player names bound to terminal slots (`SERVER_MAX_PLAYERS = MAX_TERMINALS`), plus
optional `seed` and `tick_hz` fields. `server_config()` returns the process-wide
config; `server_config_add_player()` appends a binding in terminal order.

`main()` gained `-p <name>` (repeatable). Bindings are consumed by
`make_video()` in the null backend via `server_player_name(terminal_index)`, so a
settings file's `V#n: <name>, ...` line matches an explicitly supplied name
without any environment variable or X resource database. When no `-p` is given
the name stays empty, preserving legacy v1 behavior. The X front-end continues
to use its resource database and ignores the config.

`server_init()` seeds the RNG before the first random call: an explicit
`ServerConfig.seed` if set, otherwise the pin's time()-based `init_random()`. The
seed actually used is captured so the lifecycle oracle can replay every epoch
from the same stream. (Reading the seed from server config and dropping the
`LD_PRELOAD` shim for the candidate is P1.8.)

`play_game()` now obtains each fresh match from `server_match_init()` (=
`init_combatants()` + `setup_game(TRUE)` + `game_running = TRUE`), advances via
`server_step()` (= `animate()`), and tears down via `server_match_reset()`.
`newgame`/ULTIMATE-GAME behavior is preserved. Pacing is delegated to
`server_tick_pace()`; `animate.c` is left calling the legacy pacer because the
frozen reference overlays the working `animate.c` and must not depend on
candidate-only files (the seam is wired to the pacer in P1.9).

### Lifecycle oracle (`Tests/phase1/lifecycle.sh`)

Runs `initialize -> match -> reset` twice then `destroy` in one process, with
the display-free null build, using `XTANK_LIFECYCLE=1` (only active in the
`STATE_DUMP` build, so it can never affect a normal run). It asserts:

- epoch 0 == epoch 1 == a normal single-match run == the frozen X v2 dump
  (the oracle reseeds each epoch, and the read-only v2 dump re-arms its per-tick
  diff baselines at epoch boundaries so each epoch is self-contained);
- three repeated lifecycle runs are byte-identical;
- `server_destroy()` reports `epochs=2 alive=0 dead=0 cv=null term=null`
  (no stale counts, `cv`, or terminal vehicle ownership).

The epoch-boundary reset in `animate.c` is read-only instrumentation: it never
executes in a single-epoch run, so all frozen v1/v2 values are unchanged.

  `icounter.c`. `animate.c` is intentionally not modified because the frozen
  reference overlays it and must not depend on candidate-only files.

  intent queue but no queue exists yet.
