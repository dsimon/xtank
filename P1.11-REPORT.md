## Knowledge-versus-draw separation

The seven special actions (`SP_update`, `SP_activate`, `SP_deactivate`,
`SP_toggle`, `SP_draw`, `SP_erase`, `SP_redisplay`) split into two classes.
The classification lives in `Src/Include/special.h`:

```c
#define SP_ACTION_IS_DRAW(a)  ((a)==SP_redisplay||(a)==SP_draw||(a)==SP_erase)
#define SP_ACTION_IS_MODEL(a) ((a)==SP_update||(a)==SP_activate||(a)==SP_deactivate)
```

- **Model transitions** advance simulation knowledge — mapper exploration,
  radar blips/life, stealth/camouflage surface, HUD refresh state — and always
  reach the special, with or without a terminal. They never call a draw
  primitive.
- **Draw actions** only paint an existing terminal. They are delivered only
  while presentation is active.

`do_special()` in `Src/actions.c` is the single dispatch point and enforces the
split through a new `special_invoke()` wrapper: model actions always call
`s->proc`; draw actions call `s->proc` only when
`special_presentation_active()`, and are otherwise elided (the special's
status is returned unchanged). The gate defaults **enabled**, so the X
front-end is unchanged; it is cleared by `server_set_presentation(0)`. This is
the seam P1.12 will use to stop running `display_terminal`/`update_screen_locs`
on the server without losing specials bookkeeping.

Read-only counters (`SpecialStats`) record `model_invocations`,
`draw_invocations`, `draw_suppressed`, `mapper_updates`, `radar_acquired` and
`radar_expired`. They never influence behaviour and are emitted only when
`XTANK_SPECIALS_REPORT` is set.

The mapper and radar SP_update paths were already draw-free; the radar blip
create/expire sites and the mapper scan site now bump the knowledge counters.
`special_mapper`/`special_radar`/`special_new_radar`/`special_hud` draw cases
were not restructured — the class gate makes them unreachable with no
presentation, which is exactly the property the test proves.

## Release/MVP preset

`special_apply_mvp_preset()` (`Src/program.c`), per PHASE0-BRIEF §3, permits
Console/Mapper/HUD/ordinary Radar and forces New Radar, Tac Link, Camo and Rdf
off. It writes `force_states[]`. The oracle control scenarios never call it,
so they retain all four. For this task the preset is selected by the
test-only `XTANK_MVP_PRESET` (applied in `server_match_init`); P1.14/P1.15 will
select it unconditionally for the shipped server. `XTANK_NO_PRESENTATION` and
`XTANK_SPECIALS_PROBE` are likewise test-only seams.

  `XTANK_MVP_PRESET` are test-only; unset, production/X behaviour is exactly
  the legacy behaviour.
