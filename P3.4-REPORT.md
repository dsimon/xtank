## 1. Objective

Split the Phase 2 single-peer session into **one shared coordinator** (state,
epoch, config revision, maze/Vanguard/drone selection, administrator and the
single match step/results/reset transaction) plus **two bounded peer records**
(connection/controller identity, name, readiness, transport/admission handle,
bound slot/generation, reply log and delivery cursors), keeping the listening
service alive across empty-session lobby cycles.

## 3. Audit findings

The working tree contained a complete P3.4 delegation. Audit against the plan
acceptance and the stop conditions:

- **Shared vs per-peer state is clean.** One `lobby` struct owns state/epoch/
  config/revision/admin; `struct ServerSession` owns only per-peer fields. There
  is no per-peer world, step, result or reset path. (`Src/server_session.c:110`,
  `Src/server_session.c:78`.)
- **Admin is server-assigned, never inferred from role.** `WELCOME.role` is
  always `1` (player) (`Src/server_session.c:438`); the first peer past a valid
  `HELLO` becomes administrator (`Src/server_session.c:622`), and a half-open or
  failed-handshake peer can never hold it.
- **D3-B ready/start/reset.** `READY` is an explicit `ready`/`unready` toggle
  validated against the live revision (`Src/server_session.c:693`); a config
  change increments the revision and wipes every peer's readiness
  (`Src/server_session.c:677`); `RESET` is admin-only, requires the current
  `prior_epoch`, preserves maze/drone selection, and returns through a
  `LOBBY_STATE` barrier (`Src/server_session.c:774`). Results→lobby rejoin is
  therefore open before the next start.
- **D3-E duplicate names.** Duplicate lobby names are rejected with
  `XTK_ERR_DUPLICATE_NAME`; connection/controller identity is assigned at
  accept and is independent of the name (`Src/server_session.c:596`).
- **P3.3 u8 truncation closed.** `START.vehicle_id` now carries the full `u16`
  (`Src/server_session.c:1203`); no `(uint8_t)` cast narrows any content id.
  `grep` confirms the only `u8` casts are slots/indices/drone counts.
- **Partial-failure release.** `server_session_begin()` rolls the epoch back,
  unbinds every acquired slot and resets the match on any bind / net-session /
  `server_match_init()` failure (`Src/server_session.c:1153`,
  `Src/server_session.c:1162`, `Src/server_session.c:1177`).

No stop condition is triggered (no per-peer worlds/steps, no role-derived
authority, no leaked bindings, and `RESET` is epoch-guarded so a stale reset
cannot restart/reset a newer epoch).

## 5. One-world invariants

- **One start transaction / one world init:** guarded by
  `lobby.state == LOBBY` in `server_session_begin()` and the single
  `admin`/`all_ready` check in `handle_start_request()`; no second start can run
  while `RUNNING`.
- **One `server_step()` per tick:** the production loop calls
  `server_session_step()` exactly once per iteration
  (`Src/server_session.c:1464`), independent of peer count; per-peer delivery
  happens *after* the single step.
- **One results finalization / reset:** `server_session_finish()` is
  idempotent-by-state (`if (lobby.state != RUNNING) return;`) and called once
  from `server_session_step()` or the abort/reset paths
  (`Src/server_session.c:1315`); `server_match_reset()` runs once per epoch in
  `shared_clear_match()` (`Src/server_session.c:751`).

## 10. Deferred / hand-off (bounded, documented, not hidden)

- **3 s handshake deadline** (`XTK_HANDSHAKE_TIMEOUT_MS`) and bounded admission
  fairness are P3.6; only the 2 s valid-input neutralization exists here.
- **Departure removal / admin transfer correctness across ≥2 peers** is P3.7;
  the timeout path currently aborts the whole epoch (shared TEARDOWN) rather
  than removing one combatant.
- **Per-player keyframe/view and authorized events** are P3.8; the coordinator
  already routes per-peer snapshots/events but the reliable `VIEW_KEYFRAME`
  lobby barrier is P3.8.
- **ENet connection reuse / two-peer wire re-admit** is P3.9 (the listen fixture
  documents the in-process single-peer limitation).
- **Protocol note:** the frozen `docs/PROTOCOL-v1.1.md` §8 table lists `RESET` as
  a Lobby client message; the coordinator deliberately rejects it in Lobby with
  `XTK_ERR_BAD_STATE` (safer for the "old messages must not reset" stop). This
  divergence is flagged for the `P3.8`/schema owners to reconcile; no gameplay
  effect.
