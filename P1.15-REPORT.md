## Server entry design

### Terminal-free entry point (`Src/server_main.c`, new)

`server_main.c` provides the shipped server's own `main()`; the X front-end
entry (`Src/main.c`) is **not** linked, so the legacy `make_terminal(displayname)`
fallback noted in P1.12 is never reached. It:

- parses `--maze NAME`, `--vehicle NAME`, `--drones N`, `--seed N`,
  `--matches N`, `--max-ticks N`, `--assets DIR`, `--fast`, `--version`,
  `--help`;
- resolves an explicit asset root (`--assets`, then `XTANK_SERVER_ASSETS` /
  `XTANK_ASSET_ROOT`, else relative to `/proc/self/exe`) and installs it via
  `content_set_root()` (P1.14); no environment variable is required;
- installs the approved release configuration `server_config_release()` /
  `server_release_settings()` (P1.14);
- loads the supplied maze and vehicle by explicit name through
  `make_mdesc()`/`make_vdesc()` (no directory list, no RANDOM fallback);
- builds 1–2 local drone combatants directly, replacing the graphical lobby's
  customized-combatants grid;
- runs each match through the reusable server core (`play_game()`), reports
  results and resets for the next match.

`Src/main.c` is unchanged by P1.15; it is listed in the task because the server
entry replaces its responsibilities rather than modifying it.

### Reusable core target (`Src/GNUmakefile`, `Src/Makefile.inc1`, root `GNUmakefile`)

- `phase1-server` builds `Src/xtank-server` from `SERVER_CORE_SRCS` plus
  `server_main.c`.
- `phase1-core` builds the same reusable core object set (`Src/sobj/*.o`)
  without the entry point and is what `phase1-server` and the package audit
  reuse.
- `SERVER_CORE_SRCS` = the full source list minus the X-only `XMultiSync.c`,
  minus `main.c mdesign.c vdesign.c`, minus every non-`drone` bot program
  (`SERVER_NONDRONE_PROGS`). `SERVER_COMMON_DEFS` removes `-DDYNALOAD`, so the
  server never links `-ldl`. `SERVER_ONLY_DEFS = -DSERVER_ONLY` selects the
  server-only compile paths.
- The server tree is compiled into `Src/sobj` with `-MMD -MP`; `check-x-boundary.sh
  --build` and `package.sh` inspect those `.d` files.

### Server-only seams (`Src/server_core.c`, `Src/program.c`, `Src/interface.c`)

- `server_match_init()` applies `special_apply_mvp_preset()` **unconditionally**
  under `SERVER_ONLY`; non-`SERVER_ONLY` builds (X candidate, headless oracle)
  keep the `XTANK_MVP_PRESET` environment seam so the legacy controls stay
  available to G.
- `init_prog_descs()` registers only `drone` under `SERVER_ONLY`; the full
  eleven-program set is retained otherwise, preserving four-drone/Madman oracle
  access in the harness.
- `sub_interface_design()`, `do_view()` and `display_mdesc()` compile to inert
  stubs under `SERVER_ONLY` so no designer entry point can be reached, while the
  X front-end behavior is unchanged.

## Bundle design (`Bin/package-server.sh`, new)

The script assembles a relocatable tree:

```
<bundle>/bin/xtank-server
<bundle>/share/xtank/Mazes/*.m
<bundle>/share/xtank/Vehicles/*.V
<bundle>/COPYRIGHT
<bundle>/COPYRIGHT.notes
<bundle>/BUILD-INFO
```

`server_main.c` resolves the asset root relative to `/proc/self/exe`
(`bin/../share/xtank`), so the bundle runs after being moved to any path,
including one with spaces. Only the binary, the shipped mazes/vehicles and the
two notices are copied; no build tree, object, editor, X front-end or reference
worktree is included. `--tar` optionally emits `xtank-server.tar.gz`; `BUILD-INFO`
records the binary SHA-256 and asset counts (194 maze files, 75 vehicle files).
