## 3. Implementation

### 3.1 Full-width controller identity

P3.5 §2 of the plan records that the binding APIs use a signed `int` controller
id. The session assigns the identity from a `uint32_t` counter and the wire
roster (`XTK_MSG_LOBBY_STATE`) carries a u32 `controller_id`; the `int` cast in
`bind_humans()` could therefore turn a high id negative and be *rejected*
inconsistently (the binding table rejects `< 0`, the admission layer's
`server_net_session_bind` rejects `< 0`, but a wrapped `0xFFFFFFFF` is a real
id). P3.5 makes the identity match the wire contract:

- `ServerHumanBinding.controller`, `server_players_add(const char *, uint32_t)`
  and `server_players_validate(uint32_t, int, unsigned int)` are full-width
  `uint32_t`; the complete range is a distinct identity and `0xFFFFFFFF` is not
  `-1` (`Src/Include/server.h:119`, `Src/server_players.c:71,95,201`).
- `bind_humans()` no longer narrows the id
  (`Src/server_session.c:1032`).
- `server_session_accept()` hands out ids inside the non-negative range and
  wraps back to 0 at `INT32_MAX`, so a controller id can never acquire a sign
  through the admission layer's `int` parameter and a wrapped value is only
  reused after 2³¹ assignments; any stale owner is rejected by the binding
  generation check (`Src/server_session.c:909`).

No gameplay rule, RNG order, team/setup order or content byte changed.

### 3.2 Configuration construction (already correct, now proven)

The P3.4 coordinator already builds the allowed set; P3.5 asserts it end to end:
`effective_drones()` fixes one drone for a solo human and honours 0/1/2 for two
humans (`Src/server_session.c:1008`); `bind_humans()` assigns roster-order slots
`0..n-1` (`Src/server_session.c:1022`); `build_combatants()` emits humans
(`num_players == 1`, Vanguard) then drones (`num_programs == 1`, program 0) with
distinct teams (`Src/server_session.c:1047`). `init_combatants()` resolves each
terminal-free human through its explicit binding and keeps the X-human default
(`Vehicle.teleport == TRUE`) while drones keep the bot default (`FALSE`)
(`Src/vehicle.c:243`, `Src/setup.c:195`). `server_release_settings()` supplies
the unchanged release defaults.

## 4. Acceptance results

`bash Tests/phase3/players.sh` → **P3.5 PLAYERS PASS**, 139 checks, three
byte-identical candidate repeats plus an independent rerun. Highlights:

**Allowed configurations (4 configs × 2 mazes).** `solo + 1 drone` and
`two humans + 0/1/2 drones` reach `Running` on `combat1` and `Arena`; combatant
counts are exactly 2/2/3/4; human slots are `0..h` unique; every combatant is
the Vanguard (`vdesc[..].name == "Vanguard"`); human combatants keep
`num_players == 1`, `num_programs == 0` and `teleport == TRUE`; drones keep
`num_players == 0`, `num_programs == 1` and `teleport == FALSE`; release
defaults hold (`game == COMBAT_GAME`, `team_score == FALSE`, `restart == TRUE`,
`robots_dont_win == FALSE`, `winning_score == 1000`, `game_speed == 15`).

**Two-human death/respawn and own-tank binding.** Both controllers bind only
their own slot (`validate(ca,0,ga)==1 && validate(ca,1,ga)==0`, and vice
versa); a wrong generation and an unknown controller are rejected; human A dies
through the ordinary rules and respawns while human B is untouched; ownership
survives respawn with the same controller/generation/slot and the respawned
tank is still `combatant[0]`.

**Three epochs.** Three start/reset cycles, each `Running` with the correct
epoch, unique slots `0/1`, `num_combatants == 4` and two current bindings; each
admin reset returns through the lobby barrier preserving the selection and
unbinding every controller, so the previous ownership (exact controller, slot
and generation) no longer validates.

**Duplicate names / identity.** A second peer reusing an in-use lobby name is
rejected with `XTK_ERR_DUPLICATE_NAME` and an actionable `REJECT` (code + text);
the peer is disconnected, its slot is released for a fresh identity, and the
connection/controller identity is independent of the name.

**Stale controllers and boundary identities.** `0xFFFFFFFF` is a distinct
binding identity (not `-1`); `0x80000000`, `0x7FFFFFFF` and unused ids are
rejected; a duplicate controller id is rejected; after an unbind the old owner
can no longer drive the slot; the session assigns distinct non-zero u32 ids and
a peer cannot validate another peer's controller.

**No display work / frozen trace.** No `make_terminal`, `set_terminal`,
`display_terminal`, `get_events` or `sync_terminals` call was ever made. The
bot-free two-human trace (two humans, `combat1`/Vanguard, seed `114336`,
deterministic 200-tick script, no drones), driven through the shipping
coordinator with its single shared step, prints
`PLAYERS hash-ordinary=5625b7035aae2e82 ticks=200`, byte-identical across the
three candidate repeats and equal to the independent P3.2 frozen reference
(`Tests/phase3/fixtures/players/two-human-ordinary.sha256`).
