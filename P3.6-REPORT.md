## 1. Objective

Give both peers a bounded admission opportunity and neutralisation capacity
even when one peer floods, while preserving legacy intent ordering and
at-most-once edges. `Src/intent.c` is untouched (read-only ordering/formulas).

## 3. Design and numeric bounds

### 3.1 Per-peer per-tick quotas (D3-E)

Per connected peer, per simulation tick:

- `SERVER_NET_PEER_INTENT_QUOTA = 56` non-release engine intents;
- `SERVER_NET_PEER_RELEASE_QUOTA = 4` release/neutralising intents;
- `SERVER_NET_PEER_EVENT_QUOTA = 32` routed transport events (router share of
  the global budget).

Two peers therefore occupy at most `2*(56+4) = 120` of the 128-entry engine
queue in a tick, so the 8-entry `SERVER_NET_RELEASE_RESERVE` is never consumed
by wire traffic. The reserve covers **both** peers' server-side departures
(2 intents each). The global engine bound of 128 is still enforced by
`intent_push` and by the reserve check, and `SERVER_NET_SERVICE_BUDGET = 64`
matches the frozen `XTK_MAX_SERVICE_WORK_PER_TICK` bound. Saturation is acked
explicitly with `XTK_ACK_REJECTED / XTK_ERR_QUEUE_SATURATED`.

Counters reset when the tick changes; `server_net_begin_tick` also advances a
round-robin peer-first cursor (`server_net_rotation`). In the released
two-human profile the independent per-peer quotas already make every peer's
slice starvation-free; the cursor is the tie-breaker for contended global
budget beyond two sessions.

### 3.2 Validation before intents

Every message is checked, in order, before any intent: actual transport channel
(`INPUT_BATCH`→`XTK_CH_INPUT`, `RELIABLE_CMD`→`XTK_CH_CONTROL`; wrong channel →
`XTK_ERR_BAD_CHANNEL`, no intent), peer/session routing, epoch, shared per-session
dedup window, expiry (`tick_hint + XTK_CMD_EXPIRY_TICKS`), finite/range/op, and
the binding owner/generation (`server_players_validate`). Dedup is per session,
so the same command id on different peers never collides and a channel-2 copy
followed by a channel-0 copy applies exactly once. Consume ordering in
`intent.c` is untouched; per-peer `sequence` is monotonic, so each peer's edge
order is preserved.

### 3.3 Valid-input timeout

`server_session_step` still removes a peer strictly **after** 2000 ms
(`> XTK_NEUTRAL_TIMEOUT_MS`), so 1,999/2,000 ms stay alive and 2,001 ms
removes. `last_rx_ms` is now refreshed only when a message is actually accepted:
a non-finite/out-of-range/duplicate/stale/foreign batch admits nothing and
therefore cannot extend the timeout. Neutralisation uses the top of the
sequence space (`0xFFFFFFFE`/`0xFFFFFFFF`) so it can never collide with a
peer's own admitted sequences and is ordered last within the tick.

## 4. Stop-condition audit

- Fairness does **not** change `intent_consume()` ordering — untouched.
- Release can **not** be starved: each peer has its own release quota and the
  reserve protects both server-side neutralisations.
- Invalid/replayed/foreign traffic does **not** keep a departed tank alive —
  only accepted fresh traffic refreshes the clock.
- Queues do **not** grow unbounded: per-peer quotas + reserve + engine 128 +
  router 64/32 bounds.
