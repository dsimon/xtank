## S0 — impairment capability check (DO FIRST)

Commands and output are recorded verbatim in
`~/workspace/coding/xtank-evidence/p3.14/s0/impairment-capability.txt`.

**Finding: kernel `netem` (nor `tbf`/`red`/`choke`) is NOT available here.**
The runtime has no `/lib/modules`, `modprobe sch_netem` fails, `/proc/kallsyms`
contains no `netem` symbol, and `tc qdisc add dev lo root netem delay 50ms`
returns `Error: Specified qdisc kind is unknown.` Only `pfifo`/`pfifo_fast`/
`fq_codel` (no-delay/loss/reorder) load. So tc-based link impairment is
impossible.

**But an equivalent *real UDP* impairment middlebox is available and
measured.** `tc`/root/`CAP_NET_ADMIN` exist; loopback UDP works with one
sandbox caveat: *unconnected* `sendto`/`sendmsg` returns `EPERM`, while
*connected* UDP `send()` succeeds. This is exactly why the P3.13 fixture
already links `-Wl,--wrap=sendmsg` and connects before sending. A userspace
middlebox built on real loopback UDP sockets (connected sends, ENet-style
`connect→getsockname→send→disconnect→rebind→recvfrom`) forwards real ENet
datagrams and applies delay/loss/reorder/duplicate. Proof (C probe,
`relayprobe2.c`):

```
delay_ms=0   recv=198/200 rtt_us min=25    median=51    max=694
delay_ms=20  recv=200/200 rtt_us min=40223 median=40621 max=46165
delay_ms=50  recv=200/200 rtt_us min=100244 median=100647 max=111508
```

So **symmetric 25 ms delay yields a measured ~50 ms RTT** (not 50 ms each way),
exactly as P3.14 requires. This is real packet impairment on the real UDP/ENet
path (not an in-memory transport, not silently skipped). **S0 PASS** —
proceeding with the real-socket UDP middlebox.

## S1b — relay bring-up race FIXED (2026-10-14 ~05:40Z)

Profiles/freeze re-validation under load exposed intermittent
`handshake/start failed` (~25% on reorder). Root cause was harness-only: the
relay `setup_client()` bound the server-facing `sfd` and the client-facing
`cfd` to the **same** local port P_i with SO_REUSEPORT. The kernel can hash a
client datagram into the connected `sfd`, which silently drops non-server
sources, so the relay never learns the client address and bring-up stalls; the
losing socket depends on the ephemeral-port hash, hence the flake. Fix: bind
`sfd` to a distinct ephemeral port Q_i (client still sees replies from P_i via
`cfd`; server sees c2s from Q_i and replies to Q_i). Also added `getppid()==1`
self-exit so a failed stage cannot orphan relays. No product/protocol change.
After fix: reorder-only 6/6 and full matrix green.

## S4/S5 — backpressure, replay, authz (VALIDATED 2026-10-14 ~06:13Z)

Driver corrections found and fixed while validating (all harness-only, no
product/protocol change):

1. **`stage_backpressure` awk parse.** The fixture writes the reset fields on
   one summary line; the driver's anchored `/^key=/` awk never matched, so
   "reset not exercised" was always raised. Now parses the key=value tokens.
2. **Reset restart transaction.** (a) D3-B preserves the config across a
   reset, so the fixture must NOT re-send CONFIG (that bumped the server
   revision and made the immediate READY/START stale). (b) Wait for the
   server's reliable all-ready LOBBY_STATE before sending START (READY(B) and
   START(A) ride independent ordered streams), then send START with only a
   few spaced retries. (c) Settle both clients until they observe the new
   epoch before recording it.
3. **Backpressure severity.** 20% loss / 10% reorder exceeded the delivered
   transport's operating envelope for the fixed-tick bring-up (control
   messages are acked at ENet level then quota-dropped, and ENet peers time
   out). Moderated to 5% loss / 3% reorder / 5% +50 ms — still driving
   reliable retransmits, fragment losses, queue growth and the reset
   transaction, and now 6/6 deterministic. The 30-minute *combined* profile
   remains the resilience proof at 1%.
